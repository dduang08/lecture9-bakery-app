Bakery V2 Guide

Version 2 runs the same bakery exercise with an explicit fetch, batch acceptance, pickup completion, and weekly financial totals.

Start and use the app

  1. In File Explorer, open the lecture9-bakery-app folder and choose Open in Terminal.
  2. Run python app.py and keep the terminal open.
  3. Open Bakery V2. The included database resumes the saved exercise. A fresh database starts on Monday, November 23, 2026.
  4. Check the schedule and hire a helper before fetching if you want the added capacity considered for incoming requests. Click Fetch DMs to read that day's local Instagram file.
  5. Reject any eligible new orders you don't want. Click Accept all and go to next day to review the rest in message order, close today's pickups at 5 PM, and move forward. Review outcomes in the decision log.

Screen wireframe

Exercise date                 Fetch DMs | Accept all and go to next day
Calendar week                 Order revenue | Helper cost | Difference
New requests                  Pickup schedule by date
Customer, item, time, pickup  Oven time left, revenue, cost, hire helper
Reject                        Orders booked for each pickup
Decision log                  Past pickups

Order states

New DM ── compatible ──→ Requested ── batch fits ──→ Accepted
   └─ incompatible ──→ Rejected ←─ baker rejection or batch overflow
Accepted ── 5 PM close ──→ Picked up
Accepted ── eligible change ──→ Accepted, updated
Accepted ── eligible cancellation ──→ Cancelled

Fetch checks each message against the current commitments. Requested orders do not reserve capacity. The batch checks again after each acceptance, so later requests can be rejected if earlier ones fill the day. An eligible change or cancellation applies during fetch and must match exactly one accepted order by customer and pickup date.

Data design

Exercise day → Days (date, helper booked, messages fetched)
Days 1 ─── many Orders (number, customer, product, quantity, pickup, status)
Days 1 ─── many Messages (source position, request text, outcome, order link)

The starting CSV in data/ supplies accepted orders. The seven local HTML files in data/ supply DMs. SQLite stores processing state in this version's own bakery.db. Oven usage, order revenue and helper cost are calculated from the stored facts. Revenue includes accepted and picked-up orders and excludes cancelled or rejected orders. The difference subtracts helper costs only. The weekly summary uses Monday through Sunday of the current exercise date.

Release checks

  • Data. Confirm that initial orders import once, each DM is processed once, Friday's available time and weekly revenue reconcile, and reopening preserves state.
  • Rules. Exercise the notice boundary, over-capacity rejection, helper limits, a valid change and cancellation, batch contention, and the 5 PM pickup transition.
  • Interface. Submit the actual HTML forms over HTTP. Check that controls are enabled in sequence and that feedback explains the result of each action.

The release checks ran on a temporary database copy and covered all 25 DMs through the December 1 pickups. The starting data gave Friday three free oven hours and the first week $1,960 in order revenue. In the test scenario, Saturday used all twelve hours after a helper was booked, and the batch rejected the two orders that no longer fit.
